# Aether HUD 最终效果规范 (v3)

> 版本：2026.03.26  
> 状态：Updated Draft  
> 目的：定义 HUD 的最终用户效果，统一触发方式、模式、步骤和反馈。  
> 说明：本文件描述的是最终目标，同时已对齐 `2026.03.26` 这轮左侧优先级、模式角标、右侧上下文与语言轻量化的实现方向。旧版技术说明见 `hud_specification_v2.md`。

---

## 1. 设计目标

HUD 只回答用户最关心的四件事：

1. 现在该怎么开始说
2. 它现在有没有在听
3. 它是不是已经开始替我做事
4. 这次到底成了还是没成

HUD 不应该把内部模块名、工程术语或后台流水线直接暴露给用户。

---

## 2. HUD 四区职责

HUD 固定分成四个区域，职责不能混用。

主容器应使用更接近 macOS 原生 HUD 的大连续圆角，避免出现偏方的卡片感。

| 区域 | 职责 | 规则 |
|---|---|---|
| 左 | 左侧主语义区 | 默认显示当前录音设备；强语义状态和阻塞状态允许直接覆盖设备图标。健康和模式只通过小角标表达。 |
| 中 | 当前正在发生什么 | 中间只表达当前阶段：在听、整理文字、正在输入、正在执行、完成、失败。 |
| 右 | 当前上下文 | 右侧只表示当前 App 或特殊上下文，不再重复模式信息。 |
| 语言 | 附加信息 | 语言是最弱的一层，只做轻量确认标签，不参与主状态表达。 |

### 2.1 左侧规则

左侧不是固定样式，而是按状态优先级切换渲染策略。

| 左侧策略 | 左侧表现 | 适用状态 |
|---|---|---|
| 默认设备态 | 当前录音设备主图标 + 小角标 | 在听、整理中、正在输入、正在执行、校验中、普通成功/信息反馈 |
| 强语义覆盖态 | 用强语义主图标直接覆盖设备 | 已唤醒瞬间、全文优化、拖拽等强语义状态 |
| 阻塞告警态 | 用告警/错误主图标直接覆盖设备 | 无麦克风、权限缺失、设备不可用、功能被禁用等阻塞状态 |

### 2.1.1 左侧角标位置规则

| 位置 | 内容 | 规则 |
|---|---|---|
| 左上角 | 设备健康 | 仅在 `warning / limited / error` 时出现；正常时隐藏 |
| 右下角 | 模式或结果 | 默认显示模式；当有结果反馈时由结果覆盖模式 |

规则：

1. 左上角健康角标只在异常时显示，正常时不保留占位。
2. 右下角默认是模式角标，结果反馈出现时必须覆盖模式角标。
3. 强语义覆盖态和阻塞告警态不再强行保留设备主图标。
4. 健康角标、模式角标、结果角标共用同一套圆形徽标尺寸与固定角位偏移，避免不同状态下视觉漂移。
5. 耳机左右耳图标必须优先使用与当前型号对应的精确符号；只有系统不存在该型号的左右耳符号时，才允许退回通用单耳符号或更宽泛的 fallback。

### 2.1.2 左侧健康态分档

| 分档 | 含义 | 表达方式 |
|---|---|---|
| 正常 | 当前设备可正常工作 | 不额外显示角标或只保留极弱正常感 |
| 注意 | 设备可用，但有轻微风险或切换异常 | 小黄点或黄描边角标 |
| 受限 | 设备还在工作，但系统正在降级、抑制或临时回退 | 橙色角标，允许极弱低频提醒 |
| 不可用 | 当前设备不能正常录音 | 红色错误角标 |

规则：

1. 左侧健康态只占设备图标面积的 `20% - 25%`。
2. 左侧健康态默认静态，不抢中间主状态。
3. 只有进入 `受限` 或 `不可用` 时才允许很弱的提示动效。

### 2.2 中间规则

中间区域承担全部主状态表达。  
用户是否能继续说、系统是不是已经开始做事，都必须看中间区域就能判断。

### 2.3 右侧规则

右侧只表达上下文，不重复左侧，不抢中间主状态。

优先级：

1. 当前 App 图标
2. 特殊上下文图标
3. 没有明确上下文时留空

规则：

1. `keyboard / command` 不再作为右侧默认常驻图标。
2. 交互模式的归属感放进左侧模式角标，而不是右侧。
3. 右侧尽量只回答“当前在哪个 App / 特殊上下文里”。

### 2.4 语言规则

语言是附加层，不影响左中右主语义。

显示时机：

1. 用户刚切换语言后短暂显示
2. HUD 已经可见时，用户主动需要确认当前语言
3. 不应因为语言按钮而把本来该隐藏的 HUD 长时间挂住

表现规则：

1. 语言显示为轻量短标签，例如 `中 / En / 日`。
2. 语言标签弱于左侧设备、弱于中间主状态、也弱于右侧上下文。
3. 语言标签不做重按钮感，不抢第一眼注意力。

## 3. 触发方式

产品层只有三种触发方式：

1. `按住说话`
2. `唤醒词`
3. `免提`

三种方式在空闲态必须明确区分，否则用户会混淆“它是不是一直在听”。

| 触发方式 | 空闲态 | 触发成功瞬间 | 结束后 |
|---|---|---|---|
| 按住说话 | 不显示 HUD | 按下后 HUD 立即出现并进入“在听” | 完成后直接隐藏 |
| 唤醒词 | 不显示 HUD | 唤醒成功后短暂显示“已唤醒”，然后进入“在听” | 完成后直接隐藏 |
| 免提 | 显示弱待命态 | 检测到用户开口后直接进入“在听” | 完成后回到弱待命态 |

### 3.1 触发方式的产品原则

1. `按住说话` 空闲时不能显示 HUD。
2. `唤醒词` 空闲时也不能显示“它在听你”的假象。
3. 只有 `免提` 才允许在空闲时保持弱存在。

---

## 4. 交互模式

系统内部有三种交互模式，但它们不应该直接作为用户可见文案出现。

| 系统模式 | 面向用户的含义 | HUD 主要体现位置 |
|---|---|---|
| `auto` | 系统自动判断是听写还是命令 | 左侧模式角标 + 中间后续状态 |
| `dictation` | 这次主要是往输入位置写文字 | 左侧模式角标，中间后续会进入“正在输入” |
| `command` | 这次主要是执行动作或系统命令 | 左侧模式角标，中间后续会进入“正在执行” |

规则：

1. 模式归属感应放在左侧小角标，而不是右侧独立大图标。
2. 输入模式角标使用和产品其他位置一致的“字 + 光标”符号，不再使用键盘图标。
3. 模式角标底形与其他小角标统一为圆形语言。
4. 中间不直接显示 `auto / dictation / command` 这类工程词。
5. 右侧如果没有 App/context，可直接留空。

---

## 5. 用户可感知状态模型

用户真正能感知的状态不需要很多，但必须稳定。

| 用户状态 | 是否可继续说 | 默认是否显示文字 | 中间视觉目标 |
|---|---|---|---|
| 隐藏 | 否 | 否 | 无 |
| 免提待命 | 是 | 否 | 弱存在小点或轻呼吸 |
| 已唤醒 | 很快进入下一态 | 否 | 极短唤醒确认动画 |
| 在听 | 是 | 否 | 波形、脉冲、实时收音感 |
| 整理中 | 否 | 默认否 | 文字整理或处理中动画，明确表示“已收到” |
| 正在输入 | 否 | 默认否 | 光标/输入推进感 |
| 正在执行 | 否 | 默认否 | 点击、箭头、动作推进感 |
| 正在优化 | 否 | 默认否 | 仅给慢操作使用，表达“内容正在重写/优化” |
| 校验中 | 否 | 默认否 | 只在慢校验时出现 |
| 成功 | 否 | 默认否 | 很短的成功确认 |
| 失败 | 否 | 是 | 错误图标加短文案 |

### 5.1 命名原则

用户层只使用这些词：

1. 在听
2. 整理中
3. 正在输入
4. 正在执行
5. 正在优化
6. 校验中
7. 已完成
8. 失败

不使用这些词：

1. route
2. process
3. apply
4. verify
5. dictation mode
6. command mode
7. EOS

## 6. 听写最终效果

听写不是一句话结束就立刻完成。  
普通听写在后台通常还会继续做多步处理，包括：

1. 流式纠偏
2. 自动补标点
3. 自动优化句子
4. 最终输入
5. 事后校验

这些步骤不能再以“黑箱”方式全部塞进一个模糊的处理中。

### 6.1 听写的用户态流程

| 顺序 | 用户看到的状态 | 中间区域 | 含义 |
|---|---|---|---|
| 1 | 空闲 | 无或弱待命 | 等待触发 |
| 2 | 在听 | 波形或收音动画 | 系统正在听用户说话 |
| 3 | 整理中 | 整理文字动画 | 这句话已经收到了，系统在整理最终文字 |
| 4 | 正在输入 | 输入推进动画 | 系统正在把最终文字写进目标位置 |
| 5 | 校验中 | 仅慢时显示 | 系统正在确认有没有正确写入 |
| 6 | 成功或失败 | 成功短确认，失败短提示 | 本次结束 |

### 6.2 听写后台步骤如何折叠到 HUD

| 后台步骤 | 是否对结果有影响 | 用户可见状态 |
|---|---|---|
| partial 流式追加 | 是 | 在听 |
| partial 中途纠偏 | 是 | 整理中 |
| 自动补中文句末标点 | 是 | 整理中 |
| 自动优化句子 | 是 | 整理中 |
| 去重、补后缀、差异修正 | 是 | 正在输入 |
| 输入后校验 | 是 | 默认折叠进“正在输入”，超时后单独显示“校验中” |

### 6.3 听写的关键设计要求

1. 用户停下后，HUD 必须立刻从“在听”切到“整理中”。
2. “整理中”必须表达：系统已经收到，不要重复说。
3. “整理中”必须覆盖自动加标点和自动优化句子，不再让用户感觉黑箱。
4. “正在输入”必须和“在听”完全不同，不能继续像麦克风。
5. 成功不能经常直接消失，至少要给一个很短的完成确认。
6. `PTT` 听写完成后应隐藏，`免提` 听写完成后应回到弱待命。

### 6.4 听写三种触发方式下的完整路径

| 触发方式 | 完整路径 |
|---|---|
| 按住说话 | 隐藏 -> 在听 -> 整理中 -> 正在输入 -> 成功或失败 -> 隐藏 |
| 唤醒词 | 隐藏 -> 已唤醒 -> 在听 -> 整理中 -> 正在输入 -> 成功或失败 -> 隐藏 |
| 免提 | 待命 -> 在听 -> 整理中 -> 正在输入 -> 成功或失败 -> 待命 |

---

## 7. 命令最终效果

命令流程和听写不同。  
命令的关键不是“整理句子”，而是“理解意图并执行动作”。

### 7.1 命令的用户态流程

| 顺序 | 用户看到的状态 | 中间区域 | 含义 |
|---|---|---|---|
| 1 | 空闲 | 无或弱待命 | 等待触发 |
| 2 | 在听 | 实时收音反馈 | 系统正在听用户说的话 |
| 3 | 整理中 | 理解动作动画 | 系统已经收到，正在判断要做什么 |
| 4 | 正在执行 | 动作推进动画 | 系统正在执行点击、快捷键、切换或其他命令 |
| 5 | 校验中 | 仅慢时显示 | 系统正在确认动作是否生效 |
| 6 | 成功或失败 | 成功短确认，失败短提示 | 本次结束 |

### 7.2 命令的关键设计要求

1. 命令执行过程中不能再像“还在听”。
2. “正在执行”需要明显的动作感，而不是继续显示实时转写。
3. 成功反馈要短，但必须存在。
4. 失败要说人话，例如“没听清”或“没完成”。

### 7.3 命令三种触发方式下的完整路径

| 触发方式 | 完整路径 |
|---|---|
| 按住说话 | 隐藏 -> 在听 -> 整理中 -> 正在执行 -> 成功或失败 -> 隐藏 |
| 唤醒词 | 隐藏 -> 已唤醒 -> 在听 -> 整理中 -> 正在执行 -> 成功或失败 -> 隐藏 |
| 免提 | 待命 -> 在听 -> 整理中 -> 正在执行 -> 成功或失败 -> 待命 |

---

## 8. 全文优化 / 重写类操作

这类操作通常明显比普通听写和普通命令更慢，不能继续用同样的“处理中”糊过去。

### 8.1 用户态流程

| 顺序 | 用户看到的状态 | 含义 |
|---|---|---|
| 1 | 在听 | 系统收到用户的优化需求 |
| 2 | 正在优化 | 系统正在重写、润色或整理整段内容 |
| 3 | 正在输入或正在应用 | 系统正在把优化后的结果写回去 |
| 4 | 校验中 | 系统确认内容是否已正确落地 |
| 5 | 成功或失败 | 本次结束 |

### 8.2 规则

1. `正在优化` 是少数允许保留独立慢操作视觉的状态。
2. 如果优化时间较长，可以显示极短文字辅助，但仍应以图标和动画为主。

---

## 9. 中间步骤折叠策略

HUD 不需要把所有后台步骤一比一暴露，但必须保证用户不会觉得系统进入黑箱。

### 9.1 必须单独表达的步骤

1. 在听
2. 整理中
3. 正在输入
4. 正在执行
5. 正在优化
6. 成功
7. 失败

### 9.2 可以折叠的后台步骤

| 后台步骤 | 折叠到哪个用户态 |
|---|---|
| EOS 判停 | 整理中 |
| partial correction | 整理中 |
| 自动补标点 | 整理中 |
| 自动优化句子 | 整理中 |
| 命令路由 | 整理中 |
| 命令参数准备 | 整理中 |
| 输入后快速校验 | 正在输入 或 正在执行 |

### 9.3 只有变慢时才升级显示的步骤

| 步骤 | 升级阈值 | 升级后显示 |
|---|---|---|
| 输入后校验 | 超过短阈值 | 校验中 |
| 命令执行确认 | 超过短阈值 | 校验中 |
| 全文优化 | 超过短阈值 | 正在优化 |

## 10. 左中右语言的最终状态表

| 状态 | 左 | 中 | 右 | 语言 |
|---|---|---|---|---|
| 隐藏 | 无 | 无 | 无 | 无 |
| 免提待命 | 弱待命点，可按健康态改成黄/橙/红 | 无 | 无 | 按需显示 |
| 已唤醒 | 强语义主图标覆盖设备 | 极短唤醒确认 | 当前上下文或空 | 按需显示 |
| 在听 | 当前录音设备 + 健康角标 + 模式角标 | 波形、脉冲、实时收音 | 当前 App/context 或空 | 按需显示 |
| 整理中 | 当前录音设备 + 健康角标 + 模式角标 | 整理文字动画 | 当前 App/context 或空 | 按需显示 |
| 正在输入 | 当前录音设备 + 健康角标 + 模式角标 | 输入推进动画 | 当前 App/context 或空 | 按需显示 |
| 正在执行 | 当前录音设备 + 健康角标 + 模式角标 | 动作推进动画 | 当前 App/context 或空 | 按需显示 |
| 正在优化 | 强语义主图标覆盖设备 | 优化动画 | 当前 App/context 或空 | 按需显示 |
| 校验中 | 当前录音设备 + 健康角标 + 模式角标 | 轻量确认动画 | 当前 App/context 或空 | 按需显示 |
| 成功 | 当前录音设备 + 健康角标 + 结果角标 | 极短成功确认 | 可隐藏 | 按需显示 |
| 信息反馈 | 当前录音设备 + 健康角标 + 结果角标 | 默认可无文字，必要时短提示 | 可隐藏 | 按需显示 |
| 警告/受限反馈 | 警告主图标覆盖设备 | 短提示 | 可隐藏 | 按需显示 |
| 失败/阻塞反馈 | 错误主图标覆盖设备 | 错误图标和短文案 | 可隐藏 | 按需显示 |

规则：

1. 默认链路里左侧保持设备稳定，降低用户的视觉切换成本。
2. 真正强语义或阻塞状态可以直接覆盖设备，不需要机械坚持“永远是设备”。
3. 结果优先级高于模式，必须用结果角标覆盖模式角标。
4. 右侧负责表达 App/context，不再重复模式。
5. 语言不是第四个主状态，只是附加层。
6. 模式角标本身也要和健康角标、结果角标保持同一套圆形小徽标风格。

---

## 11. 文案原则

默认尽量不用字。  
只有失败、阻塞、权限不足、无输入目标时才显示短文字。

### 11.1 建议保留的短文案

1. 没听清
2. 这里不能输入
3. 正在处理，请稍候
4. 先允许麦克风
5. 先允许语音识别
6. 没完成

### 11.2 不建议使用的文案

1. 待命中
2. 识别中
3. 路由中
4. 正在 apply
5. verify failed

---

## 12. 动画原则

1. `在听` 使用收音类动画。
2. `整理中` 使用收束和整理类动画，不再使用麦克风波形。
3. `正在输入` 使用向前推进的输入动画。
4. `正在执行` 使用动作脉冲动画。
5. `成功` 一闪即收，不拖泥带水。
6. `失败` 明确但不过度惊扰。

---

## 13. 验收标准

以下现象视为不达标：

1. `PTT` 松手后 HUD 仍空闲挂着。
2. 用户已经停下，HUD 还像在继续收音。
3. 自动补标点和自动优化句子期间，用户只看到模糊黑箱。
4. 正在输入和正在执行在视觉上分不清。
5. 成功后经常直接消失，没有确认。
6. 左侧录音设备语义被打乱。
7. 左右区域出现重复或冲突图标。
8. 语言按钮抢占主状态。
9. 右侧仍长期重复显示 `keyboard / command`。

以下现象视为达标：

1. 三种触发方式空闲态一眼能区分。
2. 说话中、说完后、执行中、结束后的差异一眼能区分。
3. 普通用户不用理解内部术语，也知道系统在做什么。
4. 听写里“自动整理文字”不再是黑箱。
5. 命令里“已经开始执行”不再像“还在听”。

---

## 14. 实施顺序建议

1. 先稳定左中右语言四区职责
2. 再统一三种触发方式的空闲态
3. 再重做“在听 -> 整理中 -> 正在输入/正在执行 -> 成功/失败”的主状态线
4. 最后再细调动画、慢操作阈值和微文案
