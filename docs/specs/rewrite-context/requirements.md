# 需求文档：全文优化上下文模型

## 简介

本文档定义 Aether `全文优化 / 全文纠错优化` 的上下文需求。

当前能力更接近“对当前输入框做一次单次改写”。这对一次性纠错足够，但不符合用户对连续写作的感知。用户真正关心的不是进程、PID 或调用次数，而是：

- 我是不是还在改同一篇内容
- 我现在属于什么写作场景
- 系统有没有逐步学会我在这个场景下的偏好

本需求文档的目标，是把 `全文优化` 从“单次工具”升级为“按写作任务连续工作的工具”。

## 目标用户

- 频繁使用 Aether 做聊天润色的普通用户
- 使用 Aether 写邮件、文档、说明文字的知识工作者
- 在编辑器、Issue、文档工具中进行技术写作的重度用户

## 术语表

- **Rewrite**：Aether 的 `全文优化 / 全文纠错优化`
- **写作任务**：用户主观感知中的同一件写作工作，例如“这封邮件”“这段聊天回复”“这篇技术说明”
- **短期上下文**：围绕同一写作任务在短时间内连续积累的上下文
- **长期偏好**：用户在某类写作场景下长期稳定的风格偏好
- **场景类型**：即时沟通、正式表达、技术写作、结构化输入
- **环境信号**：App、窗口标题、文档路径、项目目录等可观察线索
- **强信号**：能直接帮助判断“是否还是同一写作任务”的信号
- **弱信号**：只能辅助判断、不能单独决定的信号

## 产品边界

### 本次纳入范围

- 定义 `全文优化` 的产品语义和上下文继承规则
- 定义上下文的主维度、弱信号和隔离策略
- 定义 v1 可上线范围和最小可用能力

### 本次不纳入范围

- 真正的模型接线与存储实现
- 任意 App 的目录探测或项目根识别
- 复杂的云端同步与跨设备记忆
- 基于历史全文自动训练个性化模型

---

## 需求 1：系统必须按“写作任务”而不是按“调用次数”理解连续性

**用户故事：** 作为用户，我希望连续多次使用全文优化时，系统能理解我还在修改同一篇内容，而不是每次都从零开始。

### 验收标准

1. WHEN 用户在短时间内对同一篇内容连续触发 Rewrite，THE System SHALL 将其视为同一写作任务的连续优化
2. WHEN 用户仍在同一写作任务中修改内容后再次触发 Rewrite，THE System SHALL 参考该任务的短期上下文
3. WHEN 用户开始编辑明显不同的新内容，THE System SHALL 不再继承上一任务的短期上下文
4. FOR ALL Rewrite 请求，THE System SHALL 优先判断“是否是同一写作任务”，而不是优先判断“是否是同一个进程”

## 需求 2：系统必须先识别写作场景，再决定优化策略

**用户故事：** 作为用户，我希望系统根据我当前是在聊天、写邮件还是写技术文档，给出不同风格的优化结果。

### 验收标准

1. THE System SHALL 支持至少 4 类场景类型：即时沟通、正式表达、技术写作、结构化输入
2. WHEN 系统能够识别当前写作场景，THE System SHALL 优先使用该场景对应的优化策略
3. WHEN 场景变化但仍在同一 App 内，THE System SHALL 允许切换优化策略
4. FOR ALL Rewrite 请求，THE System SHALL 将 App 视为场景线索之一，而不是场景本身
5. IF 场景识别置信度不足，THEN THE System SHALL 回退到保守改写策略，而不是强行套用错误场景

## 需求 3：系统必须保留用户在特定场景下的长期偏好

**用户故事：** 作为用户，我希望系统逐步学会我在不同写作场景中的稳定偏好，例如是否更口语、是否少改结构、是否保留术语。

### 验收标准

1. THE System SHALL 支持记录用户在特定场景下的长期偏好
2. WHEN 用户在某一场景下多次接受相似风格的 Rewrite 结果，THE System SHALL 能将其总结为该场景的长期偏好
3. WHEN 用户进入不同场景，THE System SHALL 不直接复用不相容的长期偏好
4. FOR ALL 长期偏好，THE System SHALL 优先保存“风格规则”，而不是保存整段历史文本
5. THE System SHALL 允许用户关闭长期偏好记忆

## 需求 4：系统必须对不相关场景做强隔离

**用户故事：** 作为用户，我不希望聊天场景里的口语化习惯污染我的正式邮件，也不希望某个项目里的技术术语影响普通输入框。

### 验收标准

1. WHEN 用户从聊天场景切换到正式表达场景，THE System SHALL 不自动继承聊天场景的短期上下文
2. WHEN 用户从技术写作切换到普通表单或搜索框，THE System SHALL 使用更保守的最小改写策略
3. WHEN 系统判断新请求与旧任务无关，THE System SHALL 丢弃旧任务的短期上下文
4. IF 上下文复用存在较高误判风险，THEN THE System SHALL 选择隔离而不是强继承

## 需求 5：系统必须把“同一篇内容”作为最强连续性信号

**用户故事：** 作为用户，即使我换了窗口甚至换了 App，只要我还在改同一篇内容，系统就应该尽量延续刚才的优化思路。

### 验收标准

1. THE System SHALL 将内容连续性视为判断同一写作任务的最强信号
2. WHEN 同一段文本在小幅编辑后再次触发 Rewrite，THE System SHALL 仍可识别为同一写作任务
3. WHEN 内容几乎完全变化，THE System SHALL 将其识别为新任务
4. THE System SHALL 不把 PID 作为写作任务连续性的主判断依据

## 需求 6：系统必须把 App、窗口、目录降级为环境信号

**用户故事：** 作为用户，我希望系统用 App 或项目目录帮助理解场景，但不要因为我还在同一个 App 里就误以为我仍在做同一件事。

### 验收标准

1. THE System SHALL 将 App 视为环境信号，而不是上下文本体
2. THE System SHALL 将 PID 视为实现细节，而不是产品语义
3. WHEN 可用时，文档路径、项目目录、窗口标题 MAY 作为辅助信号参与判断
4. THE System SHALL 不仅因为“仍在同一 App”就自动继承短期上下文
5. IF 环境信号与内容连续性冲突，THEN THE System SHALL 优先相信内容连续性

## 需求 7：系统必须让用户能理解和控制上下文行为

**用户故事：** 作为用户，我希望知道全文优化是不是在参考上下文，以及我能否关闭、清空或限制这类记忆。

### 验收标准

1. THE System SHALL 为 Rewrite Context 提供独立开关
2. THE System SHALL 区分短期上下文与长期偏好，并允许分别清空
3. WHEN 用户关闭 Rewrite Context，THE System SHALL 回退到无上下文的单次优化行为
4. THE System SHALL 使用用户语言描述上下文行为，避免暴露 PID、进程、缓存等内部术语

## 需求 8：系统必须优先安全回退，而不是激进猜测

**用户故事：** 作为用户，我宁愿系统偶尔少记一些上下文，也不希望它把错误的风格或术语带到不相关的文本里。

### 验收标准

1. IF 上下文匹配置信度不足，THEN THE System SHALL 回退到保守无上下文改写
2. IF 系统无法确定场景类型，THEN THE System SHALL 优先保持原义和原结构
3. FOR ALL 回退路径，THE System SHALL 保持当前 Rewrite 的基础质量不低于现有单次优化
4. THE System SHALL 不因为上下文失效而阻断 Rewrite 本身

## 需求 9：系统必须可验证上下文是否提升用户结果

**用户故事：** 作为产品团队，我希望知道上下文是否真的提升了用户满意度，而不是只是增加复杂度。

### 验收标准

1. THE System SHALL 支持记录 Rewrite 是否使用了上下文
2. THE System SHALL 支持区分短期上下文命中、长期偏好命中、无上下文回退
3. THE System SHALL 支持评估“无需二次改写率”“连续改写次数”“用户撤销或重试率”等指标
4. WHEN 新上下文策略上线时，THE System SHALL 支持按阶段评估其正向收益与误判风险
