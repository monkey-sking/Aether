# 设计文档：全文优化上下文模型

## 概述

本设计文档定义 `全文优化 / 全文纠错优化` 的产品语义、上下文层级、信号优先级和 v1 落地策略。

核心决策只有一句话：

`上下文应该围绕用户感知中的同一写作任务，而不是围绕同一个 App、进程或输入框实例。`

## 设计目标

1. 让 Rewrite 从“单次润色”变成“连续写作辅助”
2. 让场景驱动优化策略，而不是让 App 直接决定风格
3. 让用户长期偏好可积累，但不污染不相关场景
4. 让系统在不确定时优先隔离和回退
5. 让 v1 可以在现有 Aether 能力上渐进落地

## 非目标

1. 不做全量历史文本回灌
2. 不做跨设备同步记忆
3. 不做任意 App 的精确项目目录识别
4. 不做自动训练式个性模型

---

## 1. 用户视角模型

### 1.1 用户真正关心的上下文

对用户来说，`全文优化`是否“有上下文”，本质上取决于 3 件事：

1. 我是不是还在改同一篇内容
2. 我现在是在什么写作场景里
3. 这个系统有没有记住我在这个场景下喜欢怎样被改

因此产品模型应拆成三层，而不是一层：

- **任务层**：同一篇内容、同一轮连续修改
- **场景层**：聊天、邮件、文档、技术写作、表单
- **偏好层**：用户长期稳定风格

### 1.2 为什么不能把 App 当主语义

同一个 App 里可能同时存在完全不同的任务：

- 浏览器里既可能是发 Slack，也可能是写邮件，也可能是填表
- 编辑器里既可能是写代码注释，也可能是写产品文档
- 微信里既可能是快速回复，也可能是发正式通知

所以 `App = 场景` 是错误建模。

App 可以帮助推断场景，但它不是场景本体。

### 1.3 为什么不能把 PID 当主语义

PID 是实现细节，不是用户任务边界：

- 进程重启会变
- 用户自己不会把“同一个 PID”理解为“同一篇内容”
- PID 对连续写作任务没有稳定产品含义

结论：PID 只能用于实现层绑定，不能进入用户语义模型。

## 2. 上下文层级

### 2.1 三层模型

#### A. 短期任务上下文

用途：
- 解决“同一篇内容连续优化”问题
- 让第二次、第三次 Rewrite 不再像第一次那样从零开始

内容形式：
- 最近几次已接受的改写方向
- 当前任务的场景类型
- 当前任务的局部风格约束

不建议直接保存：
- 大量原文全文
- 无边界增长的 before/after 历史

#### B. 场景偏好上下文

用途：
- 解决“用户在某类场景里一贯怎么写”问题

内容形式：
- 更口语 / 更正式
- 少改结构 / 允许重组句子
- 保留术语 / 保留英文 / 不改项目名
- 输出更短 / 更完整

#### C. 环境线索上下文

用途：
- 作为识别任务和场景的信号，不直接主导决策

信号示例：
- App bundle
- 窗口标题
- 文档路径
- 项目目录
- 焦点输入元素特征

### 2.2 优先级

上下文判断优先级固定为：

1. **内容连续性**
2. **场景类型**
3. **用户长期偏好**
4. **环境信号**

其中：

- 内容连续性决定“是不是同一任务”
- 场景类型决定“应该怎么改”
- 用户长期偏好决定“在这个场景里偏向怎么改”
- 环境信号只用于辅助判断前 3 项

---

## 3. 场景类型模型

### 3.1 v1 场景集合

#### 即时沟通

典型场景：
- 微信、Slack、Discord、聊天输入框、评论回复

优化目标：
- 自然、短、像人说话
- 减少过度正式化
- 允许轻微口语润色

#### 正式表达

典型场景：
- 邮件、说明文档、公告、申请、正式消息

优化目标：
- 清晰、完整、稳
- 句子更顺，但不过度扩写
- 保留礼貌和逻辑层次

#### 技术写作

典型场景：
- Issue、PR 描述、注释、技术文档、代码相关说明

优化目标：
- 保留术语和代码标识
- 保留技术结构
- 避免把精确术语“润色掉”

#### 结构化输入

典型场景：
- 搜索框、标题、表单字段、简短输入项

优化目标：
- 最小改动
- 尽量不扩写
- 只修明显错误

### 3.2 场景切换原则

- 同一 App 内允许场景切换
- 同一任务内优先保持场景稳定
- 场景不确定时回退到保守策略

---

## 4. 写作任务识别模型

### 4.1 任务连续性的主判断

系统应优先判断：

`用户是否仍在处理同一篇内容`

而不是：

- 是否仍在同一 App
- 是否仍在同一 PID
- 是否仍在同一窗口实例

### 4.2 强信号

强信号按顺序如下：

1. **内容相似性**
当前文本与最近一次 Rewrite 后文本高度相似，只做了局部编辑

2. **时间邻近性**
两次 Rewrite 发生在短时间窗口内

3. **任务内场景稳定**
同一段内容持续落在同一场景类型

### 4.3 弱信号

弱信号包括：

- 同一 App
- 同一窗口标题
- 同一输入元素指纹
- 同一文档路径
- 同一项目目录

弱信号只能帮助提高或降低置信度，不能单独决定“仍是同一任务”。

### 4.4 任务结束条件

出现以下任一情况，应视为进入新任务：

- 文本主体明显变化
- 用户切换到明显不同的场景类型
- 连续时间窗口过期
- 用户主动清空或关闭上下文

---

## 5. 隔离策略

### 5.1 必须隔离的组合

- 即时沟通 -> 正式表达
- 技术写作 -> 普通表单
- 某项目技术术语 -> 无关普通输入
- 低置信度旧任务 -> 新任务

### 5.2 可以尝试继承的组合

- 同一篇内容的小幅连续修改
- 同一封邮件的连续润色
- 同一段聊天回复的连续变体调整
- 同一项目技术文档的连续修改

### 5.3 回退原则

如果无法确定是否应继承上下文，默认：

- 继续当前 Rewrite
- 但不继承旧任务短期上下文
- 只保留全局安全偏好或直接无上下文

---

## 6. v1 落地策略

### 6.1 产品语义与实现近似

用户语义上，最理想的主键是：

`写作任务 = 同一篇内容 + 同一场景`

但 v1 不需要也不应该等到“完美识别”才开始做。

v1 可以用“用户语义优先、实现信号近似”的方式分层落地：

- **任务层近似**：用内容相似性 + 时间窗口识别“同一篇内容”
- **场景层近似**：用 App、窗口和输入特征推断场景
- **偏好层近似**：按场景存用户长期风格，不存大量历史原文

### 6.2 v1 推荐主键

#### 短期任务上下文

推荐键：

`taskContext ~= 内容签名 + 场景类型 + 短时间窗口`

说明：
- 主体由内容连续性决定
- 场景类型作为任务约束
- App、窗口标题、输入元素仅用于置信度加权

#### 长期偏好上下文

推荐键：

`preferenceContext = 用户 + 场景类型 (+ 可选 App 类别)`

说明：
- 偏好应该按场景保存
- 不应以 PID 或单一 App 作为长期偏好键

### 6.3 v1 不建议的方案

- 不建议按 PID 记忆
- 不建议按“原文全文”直接做唯一主键
- 不建议无边界地把 before/after 全部回灌给模型
- 不建议把“目录级上下文”作为所有场景的 v1 核心能力

---

## 7. 环境信号的产品定位

### 7.1 App

定位：
- 场景线索
- 术语线索
- 风险约束

不是：
- 写作任务主键
- 长期偏好唯一键

### 7.2 窗口标题

定位：
- 有助于分辨“同一文档 / 同一聊天线程 / 同一页面”

风险：
- 容易变化
- 浏览器页签标题噪音大

### 7.3 文档路径 / 项目目录

定位：
- 对技术写作场景价值高
- 更适合作为术语和项目名约束来源

风险：
- 通用性差
- 很多 App 没有稳定暴露
- 不适合作为通用场景的唯一主语义

结论：
- 目录级上下文应是技术写作增强项，不应成为通用 Rewrite Context 的基础假设

---

## 8. Prompt 组装原则

### 8.1 上下文注入内容

应优先注入：

- 当前场景类型
- 当前任务的短期约束摘要
- 用户在该场景下的长期偏好摘要
- 当前任务必须保留的术语/风格约束

### 8.2 不应直接注入的内容

- 无边界原始历史全文
- 不相关场景的旧 before/after
- 仅靠 App 绑定的大段历史

### 8.3 上下文摘要格式

推荐将上下文压缩成规则，而不是全文：

- 场景：技术写作
- 当前任务约束：保留英文 API 名、少改列表结构
- 用户偏好：倾向简洁、不过度正式
- 项目术语：Aether, HUD, Rewrite, Dictation

---

## 9. 用户控制与可解释性

### 9.1 用户可见能力

用户需要理解的是：

- 全文优化是否正在参考上下文
- 参考的是“当前写作任务”还是“长期偏好”
- 如何关闭或清空这些记忆

### 9.2 用户文案原则

应写成：

- “继续参考这篇内容最近的优化方式”
- “记住你在聊天/邮件中的常用风格”

不应写成：

- “复用 PID 级缓存”
- “命中 app-scoped memory”

---

## 10. 指标与验证

### 10.1 关键指标

- 连续二次 Rewrite 成功率
- 无需第三次继续改的比例
- 误继承导致的重试率
- 用户关闭上下文功能的比例
- 各场景下的接受率差异

### 10.2 验证分层

#### 产品验证

- 同一任务连续润色是否更稳定
- 聊天与正式写作是否明显分化
- 技术写作是否更少出现术语漂移

#### 风险验证

- 错误场景继承
- 错误长期偏好污染
- 目录/项目词污染普通输入

---

## 11. 决策记录

### DR-1

`全文优化` 的主语义从“单次输入框改写”升级为“围绕写作任务工作的连续优化”。

### DR-2

产品层不采用 `PID` 作为上下文主键。PID 只能作为内部实现绑定信号。

### DR-3

产品层不采用 `App` 作为上下文本体。App 只能作为场景和术语线索。

### DR-4

v1 的主模型采用：

- 短期：同一篇内容 + 同一场景
- 长期：按场景沉淀用户偏好
- 环境：App / 窗口 / 目录作为辅助信号
